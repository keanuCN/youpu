# 「有谱」技术设计方案

> 万物参数图鉴 + 客观分析 + 社区评价的装备选择网站
> 口号：买之前，来有谱。
> 版本：v1.3 ｜ 日期：2026-09-14（v1.3 新增：后台管理系统 §16，数据源真理切换为 PG；v1.2 外部参考与复用策略 §15、Crawlee 选型；v1.1 埋点 §12、安全 §13、SEO §14、推荐引擎 AI 混合架构 §6）

---

## 1. 项目定位

- **产品本质**：结构化装备参数库（图鉴）+ 横向对比 + 按条件推荐 + 社区评分评论
- **首发品类**：滑雪-单板（创始人熟悉该领域，作为数据质量与内容判断的兜底）
- **扩展路线**：单板 → 双板/雪鞋/固定器 → 跑步鞋/镜头/键盘等任意品类（架构按多品类设计，新增品类零代码改动）
- **目标市场**：中文用户，PC 端为主、移动端兼顾
- **流量策略**：中文 SEO 主战场在微信搜一搜/知乎/小红书，榜单页与分享卡图按此设计
- **盈利**：v1 不做，架构预留（联盟链接/广告位后置）

### 成功标准（v1）
网站上线可用：数据准确、图鉴精致、对比与推荐真实有效、社区评价跑通冷启动。

### 明确不做（Out of Scope）
英文市场、纯 AI 无人工审核内容、自建电商、盈利功能、移动端专属交互。

## 2. 总体架构

```
                      ┌──────────────── 腾讯云 CVM ────────────────┐
 用户(PC为主) ← Nginx ←   Next.js 前端 (SSR)                      │
                            │ REST/JSON                            │
                        NestJS 后端 API                            │
                         │        │        │                       │
                     PostgreSQL   Redis   Elasticsearch(ik分词)     │
 数据采集/录入脚本 ──→   (数据+缓存)              (搜索+筛选)        │
 定时任务(备份/同步)     COS 对象存储(产品图/分享卡图) + CDN          │
                      └────────────────────────────────────────────┘
```

- 前后端分离；前端为 Next.js（SSR），保证微信搜一搜/搜狗/Bing 可抓取、知乎链接预览正常。
- 数据录入：Git 管理的 YAML + seed 管线（数据护城河版本化）；M3 后视需要演进出后台。

## 3. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Next.js 14 + TypeScript + Tailwind CSS | SSR 保 SEO；断点兼顾移动端降级可用 |
| 后端 | NestJS + TypeScript | 与前端共享类型；单人全栈提效 |
| 数据库 | PostgreSQL 16 | JSONB 支撑多品类动态属性 |
| 搜索 | Elasticsearch 8.x + analysis-ik | 自定义镜像装 IK 中文分词；search_as_you_type 联想；聚合做筛选联动 |
| 缓存 | Redis | 对比/榜单/聚合结果缓存；通知/会话辅助 |
| 图片 | 腾讯云 COS + CDN | 图片是本站最大带宽项，不入服务器磁盘 |
| 认证 | Passport-JWT（Access + Refresh Token） | 登录态需参与 SSR 渲染，middleware 统一处理 |
| **后台管理** | **Refine + Ant Design 5**（apps/admin 独立 SPA） | 一步到位自研（§16）：spec_schema 动态表单、审核队列、配置中心全可控；与 web/api 共享 packages/schema 类型 |
| 部署 | Docker Compose + Nginx + GitHub Actions | 镜像推腾讯云 TCR，SSH 部署 |
| 数据采集 | **Crawlee**（Apify 开源） | Node 爬虫框架：重试/反检测/队列自带，替代裸 Playwright 自研调度 |
| 包管理 | pnpm monorepo | 见 §4 目录结构 |

服务器建议：**4C8G 起**（ES 堆内存 1–2G，与 PG/Redis 共存的底线）；4C4G 需压缩 ES 参数。

## 5. 数据模型（多品类核心设计）

**原则：类目定义属性 schema，产品数据用 JSONB；新增品类 = 插一条 category + 录数据。**

> **术语与结构对齐 PIM 行业标准**（Akeneo/Unopim 十年沉淀的属性模型，定稿 spec_schema 前通读其文档，避免自创概念）：
> `spec_schema.fields` ≈ PIM Attribute；`enum options` ≈ Attribute Options；字段的 `group`（分组展示）≈ Attribute Group；"某类目使用哪套字段集" ≈ Family。将来若需迁移到专业 PIM 或引入相关工具，映射是平移而不是重构。

```sql
category   (id, slug, name, parent_id, spec_schema JSONB)
  -- spec_schema 声明字段：名称/类型(number|enum|mult_enum|nested)/区间/是否参与筛选与对比
  -- 并声明推荐打分权重配置
brand      (id, name, logo_url, country)
product    (id, category_id, brand_id, model, year,
            title, one_liner, price_range,
            specs JSONB,                       -- {length:"152", flex:8, terrain:["all-mountain"]}
            rating_agg JSONB,                  -- 社区评分实时聚合回写(综合+分项)
            favorite_count, search_vector tsvector,
            status)                            -- draft/published
product_image (id, product_id, url, kind)      -- 底面/正面/侧面/板型示意
rating     (id, user_id, product_id, overall, sub JSONB,  -- 分项：弹性/稳定/容错/性价比
            rider_profile JSONB,               -- 雪龄/身高/常去雪场(评论可信度标签)
            created_at)
review_vote (rating_id, user_id, helpful)      -- "有帮助"投票
user       (id, email, nickname, avatar, rider_profile JSONB,
            status, created_at)                -- 反垃圾：注册24h内不可评论
favorite   (user_id, product_id, created_at)
notification (user_id, type, payload JSONB, read)
ranking    (id, category_id, slug, title, method)  -- 赛季榜单：社区投票+数据
rank_entry (ranking_id, product_id, position, score, note)
compare_history (user_id, product_ids, created_at) -- 留存：我的对比历史
```

### 滑雪板 spec_schema 字段清单（首发类目）

| 字段 | 类型 | 参与筛选 | 参与对比 |
|---|---|---|---|
| 长度档位/尺寸表 | nested(长度↔身高/体重区间) | – | ✓ |
| 硬度 | number 1–10 | ✓ | ✓ |
| 板型 | enum Camber/Rocker/混合 | ✓ | ✓ |
| 方向 | enum 双向/定向 | ✓ | ✓ |
| 适用场景 | mult_enum 全山地/公园/刻滑/野雪/新手 | ✓ | ✓ |
| 有效边长 / 板腰宽 / 转径 | number(mm) | 板腰宽✓ | ✓ |
| 价格区间、上市年份 | – | ✓ | ✓ |
| 一句话点评 | text(人工撰写，AI 润色) | – | – |

### 推荐引擎（规则候选 + AI 解释的混合架构）

**总原则：产品推荐永远出自确定性规则，AI 不直接"选品"**——候选集的正确性由数据与规则保证，AI 只负责理解用户和解释结果。彻底杜绝幻觉推荐。

**双入口，同一管线：**
```
问卷模式(v1)：结构化问卷 ──┐
                            ├→ 规则管线(硬过滤→打分→Top3) → AI 重排解释 → 结果
对话模式(v1.5)：AI 多轮追问 → 问卷JSON ─┘
```

**数据正确性的四层保障：**
1. **领域映射表 = 人写规则**（创始人的专业知识资产）：身高/体重 → 板长区间、水平 → 硬度区间、场景 → 板型/参数偏好权重。v1.3 起存于 `config_rule` 表（DB 版本化，后台配置中心编辑，见 §16.2），初始版本仍以 Git 中的 YAML 导入评审，双轨一致。
2. **规则打分（确定性）**：硬过滤（尺寸表匹配、预算）→ 加权排序：场景 40% ｜ 水平 30% ｜ 硬度适配 20% ｜ 价格 10% → 产出 Top3 候选。此阶段零 AI。
3. **AI 职责（三件事）**：
   - 候选**同分重排**：结合社区评价文本判断哪块板"真实口碑"更适合该用户
   - **个性化理由生成**：引用问卷与参数生成"为什么推给你"
   - **对话式抽取**：把用户自然语言（"我 175 80公斤 想玩公园"）解析为问卷 JSON（zod schema 校验）
4. **反幻觉护栏**：LLM 输出用 zod 校验；提及的产品 id 必须在候选集内；引用的数值必须与产品 specs 程序化一致；校验失败自动降级为纯模板文案。

**对话模式实现要点**：LLM function calling，工具只有 `set_survey_field` / `submit_survey`（不允许搜索、不允许推荐），最多 6 轮追问；结束仍走同一规则管线。

**工程细节**：
- 模型：DeepSeek/腾讯混元 API（境内直连、可过备案主体合规），超时 5s / 校验失败 → 模板降级
- 成本：结果缓存 key=问卷参数哈希（TTL 1 天）；AI 理由随结果一起缓存；预计月成本 <¥50
- 质检闭环：新增 `recommend_log (survey JSONB, candidates uuid[], llm_output JSONB, rule_version, model, created_at)`，每周抽样人工复核 → 修正映射表配置（映射表是活资产）
- 权重/阈值/映射表调优只改配置不发版

### 客观分析引擎（核心差异化）
- 洞察规则库：每条规则 = 触发条件 + 文案模板
  - 例：`flex >= 7 && level == 'beginner'` → "硬度 {flex}/10：需要至少一个雪季经验才能压住，新手慎选"
  - 例：`waist < 250 && user_note boot_size >= 43` → "板腰 {waist}mm：大脚用户需确认 boot 突出量"
- 详情页实时生成；参数缺失的板块自动隐藏。措辞迭代只改配置。

## 7. 前端页面与交互

### 信息架构
```
首页(杂志式：品类入口+本周新品+高分榜+社区热评)
└─ 品类树：运动 → 滑雪 → 单板列表(首发落地页)
     ├─ 详情页
     ├─ 对比页(对比坞发起)
     ├─ 榜单页(赛季榜)
     ├─ 推荐问卷页
     └─ 个人中心(收藏/对比历史/我的评论/通知)
```

### 关键交互
1. **列表页**：PC 4 列大图卡片网格；左栏筛选（场景/硬度/价格/品牌/年份）；排序（热度/新品/评分/硬核值）；卡片 hover 快捷动作 `＋对比 ＋收藏 详情`——对比入口必须在列表页直达。
2. **常驻对比坞**：任意页面加入对比 → 底部 dock（最多 4 块、跨页常驻、可移除）→ 对比页全参数横表 + 差异行自动高亮 + 多维雷达图叠放。
3. **详情页**：图集（底面主视觉）→ 右栏价格带/评分分布/硬度条/"适合谁"标签 → 客观分析区 → 参数全表 → 分项评分+雷达图 → 评论区（按"有帮助"排序，评论者雪龄/身高/雪场标签外显）→ 同场景竞品对比入口。
4. **移动端降级**：筛选收抽屉、对比列左右滑动；不做专属交互。

### 留存机制（v1 做前三条）
- 收藏/关注 + 个人中心聚合
- 评论被回复/点赞 → 站内通知
- 赛季榜单：社区投票 + 数据共同生成，制造回访节点

## 8. 用户体系与反垃圾

> 本节只覆盖社区内容风控；全站反机器人/反恶意攻击/防盗爬见 §13。

| 项 | 方案 |
|---|---|
| 登录 | v1 邮箱验证码；v2 微信/QQ OAuth（个人主体拿不到微信开放平台资质，后置） |
| 评论门槛 | 注册满 24h 方可评论/打分；新用户带默认昵称 |
| 审核 | 先发后审 + 敏感词过滤 + 举报队列（量大再加人工） |
| 评分聚合 | 写时异步聚合回写 product + ES，避免读时现算 |
| 可信度 | rider_profile 标签外显，"同条件的人怎么看"是信任机制核心 |

## 9. 部署与运维

### Docker Compose 服务
`nginx / web / api / postgres / redis / elasticsearch(自定义 ik 镜像)`

- Nginx：统一入口、HTTPS（腾讯云免费证书）、`/api` 转发、静态资源缓存
- CI/CD：push main → GitHub Actions 构建镜像 → 推腾讯云 TCR → SSH `docker compose up -d`
- 备份：PG 每日 pg_dump → 传 COS（异地）；ES 可从 YAML 源重建，不做快照；COS 图片为独立存储无需备份
- 图片管线：采集 → 压缩 webp → 生成 3:4 竖版分享卡图（小红书素材，脚本自动化）

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 单机 ES+PG+Redis 内存不足 | 4C8G 起步；ES 堆 1–2G、禁用 ML 节点；监控告警 |
| 数据录入倦怠 | 采集脚本产 YAML 草稿，人工只做校对；每周固定补 5 款节奏 |
| 中文搜索流量起不来 | 主渠道为小红书/知乎内容，榜单页按"可分享"设计 |
| 评论冷启动 | 上线前邀请雪友群种子用户灌 50+ 真实评论 |
| 品牌图片版权 | 详情页标注来源；长期转向自制示意图/实拍 |
| 参数库被爬虫成建制搬走 | 防盗爬是安全设计一等公民，见 §13（API 最小字段/匿名对比限次/溯源水印） |
| 大流量 DDoS 导致 IP 黑洞 | 免费防护仅 ~10G，黑洞预案：数据在 COS+快照，可迁移重建；长期靠 CDN 收敛入口 |
| AI 推荐理由出错/幻觉 | 候选与数值程序化校验，校验失败降级模板文案；recommend_log 抽样人审，见 §6 |

## 12. 埋点与数据分析

### 12.1 工具分层

| 层 | 工具 | 说明 |
|---|---|---|
| 流量指标 | **Umami 自托管**（compose 加一个容器） | PV/UV/来源/设备/着陆页，零第三方依赖，数据在自己库里 |
| 业务事件 | 自研轻埋点：前端 `track()` SDK → `POST /api/events` → Redis Stream → worker 批量落 PG `event` 表 | 只记决策需要的事件，拒绝"全埋点"幻觉 |
| 中文搜索词报告 | 可选叠加百度统计（免费版） | 唯一能看到中文搜索词的渠道；主渠道 Bing/搜狗站长平台自带 |

`event` 表：`id bigint, anon_id uuid, account_id uuid NULL, name text, props JSONB, created_at`——按月分区，保留 18 个月后归档 COS。匿名 ID 存 localStorage/cookie，IP 入库前哈希（隐私合规）。

### 12.2 事件字典（v1 必埋，命名即规范）

| 事件 | 触发时机 | 关键属性 |
|---|---|---|
| `expose` | 产品卡片进入视口（IntersectionObserver） | category, product_id, position, sort |
| `card_click` / `detail_view` | 点击卡片 / 详情曝光 | product_id, from(list/search/ranking/compare) |
| `compare_add` / `compare_open` | 加入对比坞 / 打开对比页 | product_ids, source |
| `recommend_start` / `recommend_complete` | 问卷开始 / 出结果 | survey, result_ids, fallback(bool) |
| `search` | 搜索提交 | query, hits |
| `favorite_add` / `rating_submit` / `reply_submit` | 收藏 / 评分 / 回复 | product_id / rating_id |
| `signup` / `email_verify` | 注册漏斗 | channel(referrer) |
| `share_card_download` | 下载 3:4 卡图 | product_id |
| `outbound_click` | 跳外部（电商/官网，为联盟预留） | product_id, target_domain |

### 12.3 核心漏斗与报表

```
着陆 → 看详情 → 加入对比 → (推荐问卷完成) → 收藏/评分/注册
```
- **北极星指标**：周活跃"完成对比或推荐"用户数（对"帮用户做决策"这一价值的直接代理）
- 每周一脚本自动产出：漏斗转化率、类目热度榜、**零结果/低结果搜索词清单**——后者就是下周的数据补充与榜单选题清单，数据驱动运营的具体形态
- 推荐质量周报：recommend_log 抽样 + 问卷放弃率 → 反馈映射表调优

## 13. 安全设计（反机器人 / 反恶意攻击）

### 13.1 攻击面清单（本站特殊性：参数库就是资产本体）

| # | 威胁 | 后果 | 优先级 |
|---|---|---|---|
| 1 | **爬虫成建制偷参数库** | 护城河归零，别人站比你先建成 | ★★★ 本站第一威胁 |
| 2 | 注册机 + 灌水刷评 | 社区信任崩坏 | ★★★ |
| 3 | 验证码轰炸（邮箱/短信滥用） | 费用损失 + 发信域名信誉污染 | ★★ |
| 4 | 撞库/暴力破解 | 账号接管 | ★★ |
| 5 | CC / 洪水 DDoS | 服务不可用、IP 黑洞 | ★★ |
| 6 | 通用 Web 攻击（注入/XSS/CSRF） | 数据泄露 | ★（框架+纪律兜底） |

### 13.2 分层防御

**网络层（CVM/安全组）**
- 安全组只放行 80/443 + 白名单 IP 的 SSH（改端口、仅密钥登录、fail2ban）
- PG/Redis/ES **只绑内网地址**，compose 网络不对公网暴露端口——单条做错即可被拖库
- `unattended-upgrades` 自动安全补丁；腾讯云 DDoS 基础防护默认开启

**网关层（Nginx）**
- `limit_req`：页面 10r/s、API 5r/s per IP（burst 30）；`limit_conn` 并发连接限制
- HSTS、CSP、X-Frame-Options、`Referrer-Policy`、隐藏版本号
- 异常流量突增 → 自动升级全站只读页（见下"降级预案"）

**应用层**
- NestJS Throttler 按角色分桶：匿名 / 登录 / 管理员，敏感接口（登录、发码、评论、收藏、对比）单独收紧
- **验证码**：腾讯 T-Captcha（有免费额度）——注册与发码必挂；评论按风险触发（新号/高频才弹，不打扰真人）
- 发码防滥用：同邮箱 / 同 IP / 同设备指纹各 3 次/日；邮件走 SES 类服务避免轰炸与信誉污染
- 评论写路径全链：敏感词 → 链接数限制 → 注册 24h 冷却 → 接口限频
- 用户资料提交一律 zod schema 白名单校验，杜绝 mass-assignment

**防盗爬专项（威胁 1 的对策）**
- API 最小返回原则：列表页不返回全量 specs（点开详情才有），批量枚举型参数（`offset>1000`、翻页过深）触发验证码
- **匿名对比限 20 次/日，超限需登录**——反盗爬与获客（注册）同一步完成
- 溯源水印（可选，量大后启用）：对比响应中嵌入用户相关微差异（评分小数位、排序扰动），泄露样本可反查内鬼/账号
- robots.txt 引导 + 全站 sitemap 给合法爬虫，减少百度式乱抓浪费带宽

**数据层**
- DB 角色分离：web 应用（只读写业务表）/ migration（DDL）/ 备份（只读），最小权限
- 密钥：`.env` 不进仓库；CI 用 Actions Secrets；TCR 用只拉取子账号凭证；定期轮换
- 供应链：CI 加 `pnpm audit` 门禁 + Renovate 自动升级基础镜像 + trivy 扫描

### 13.3 通用 Web 攻击纪律

- SQL 全走 Prisma 参数化，raw query 需 code review 标注原因
- 评论渲染：`DOMPurify` sanitize + 纯文本换行策略，**永不开放富文本/HTML**
- CSRF：API 走 Authorization header（天然免疫）；SSR 会话 cookie `HttpOnly + SameSite=Lax`
- 上传（头像）：类型白名单 + 图片重编码去载荷 + COS 直传（不过服务器）

### 13.4 降级预案与监控告警

| 场景 | 预案 |
|---|---|
| 被 DDoS 且 IP 进黑洞 | 腾讯云数据（PG 备份在 COS）→ 换机恢复，RTO 半天；域名走 COS+CDN 静态降级页 |
| 注册/评论事件突增（灌水特征） | 自动批量 `status=pending` 待审 + 通知本人微信 |
| 磁盘 >80% / ES 堆 >90% / SSL 30 天到期 | 腾讯云监控 + 脚本告警（Server酱/企微机器人推微信） |

**备份即安全的一部分**：每日 pg_dump 版本化桶存 30 天 + **每季度恢复演练一次**——没演练过的备份等于没有备份。

## 14. SEO 与内容分发方案

### 14.1 页面 × 关键词意图矩阵（每类页面各司其职）

| 页面 | 目标意图 | 例词 | 备注 |
|---|---|---|---|
| 列表页 | 泛品类词 | 滑雪板怎么选 / 单板推荐 | 权重靠内链聚合 |

| 对比页 | 双词（金矿） | Custom vs Dream /  Jones 新手板对比 | URL 可分享即收录，中文圈几乎无人做结构化对比页 |
| 榜单页 | 决策词 | 2026 新手第一块板 / 女款单板推荐 | 主要分发弹药，兼顾小红书/知乎 |
| 参数工具页 | 参数词 | 身高175滑雪板多长 / 板腰宽对照 | **推荐问卷页复用为着陆页**，一物两用 |

### 14.2 站内技术件（M2 随内测站一并完成）

- **标题/描述模板**：`{model} {year} 参数·社区评分·尺寸怎么选 - {brand} | 有谱`，全部从结构化数据生成，无重复
- **canonical 纪律**：筛选/排序参数 URL 一律 `noindex`（只让干净路径进索引）；分页 self-canonical + `rel=next/prev` 标记
- **JSON-LD 结构化数据**：`Product + AggregateRating`（详情页评分进富摘要）、`ItemList`（榜单）、`BreadcrumbList`、`FAQPage`（客观分析区块复用）
- **sitemap**：自动生成 + 分组（products/rankings/compares），发布时主动推送 Bing/搜狗；robots.txt 声明
- 图片：文件名=型号+关键词、alt 规范、LCP 图 preload、其余懒加载；CWV 桌面全绿，移动端 LCP < 2.5s
- **内链四件套**：详情 ↔ 品牌页 ↔ 所属榜单 ↔ "同场景竞品对比"模块（每页都留一条走向转化页的路）
- `noindex` 白名单：个人中心、搜索结果页、推荐会话页、登录后所有页面

### 14.3 中文渠道现实（决定投入比例）

```
实际性价比排序：Bing CN ≈ 搜狗/微信搜一搜 > 知乎站内SEO > 百度（个人站歧视重，不做主战场）
```
- 各站长平台**上线当天注册**并验证：Bing Webmaster（国内=CN Bing）、搜狗（吃微信搜一搜）、百度（顺手提交，不指望）
- **微信搜一搜**：注册同名公众号，榜单内容公众号先发一文 → 站内同文规范引用——搜一搜收录以公众号为主载体
- **知乎**：长文（"身高体重怎么对应板长"）内嵌对比表格截图 + 详情/工具页链接，知乎答案在 Bing/百度权重高且寿命长
- **小红书**：站是"货架"，小红书是"流量口"。卡图 + 评论区引导搜索"有谱"（平台拦外链是既定事实，养品牌词搜索心智）

### 14.4 内容红线与节奏

- **数据页允许 AI 辅助成文，判断与一句话点评必须人审**——纯 AI 批量页在中外搜索引擎都是打击对象，且杀社区信任（与 §6 推荐引擎同一原则）

## 15. 外部参考与复用策略

> 结论：GitHub 实际调研（2026-09）未发现"参数图鉴+对比+推荐+评价"复合形态的可复用开源项目——**核心产品逻辑必须自研，这正是护城河所在**。以下轮子用于砍苦力活。

### 15.1 可直接采用的组件

| 项目 | 规模 | 用途 | 决策 |
|---|---|---|---|
| **Crawlee**（apify 开源） | Node/TS 爬虫框架 | 品牌官网参数采集，替代裸 Playwright 自研调度（重试/反检测/队列自带） | ✅ 进 §4 scripts，M2 使用 |
| **Umami** | 自托管分析 | 流量指标，见 §12 | ✅ M1 进 compose |
| ~~**Payload CMS**~~ | 44.7k★ TS | ~~可视化录入后台~~ | ❌ v1.3 弃用：后台走自研 Refine（§16），Payload 接管数据层的模式与自建 Prisma schema 冲突 |

### 15.2 只抄思想、不引入的技术栈

| 项目 | 抄什么 |
|---|---|
| **Akeneo / Unopim**（PIM，PHP） | 属性模型术语与结构：Attribute / Attribute Options / Attribute Group / Family → 对齐 `spec_schema` 设计（§5），保证未来可迁移 |
| **UserRank / OpenBenchmarking**（众包跑分/榜单站，同类目最聪明的开源近亲） | 评分聚合口径、防刷结构、榜单数据组织；M1 定 schema 前读其公开数据模型 |
| **MedusaJS**（NestJS 系） | NestJS + PG + Redis 的插件式模块组织范式（module 边界、DI 用法），不引入其 commerce 依赖 |

### 15.3 明确不复用的方向

- **Directus**：接管 PG schema 管理权，与 Prisma migrations / 自定义 outbox_event 管线冲突，单人项目双 head 必打架
- **整套电商框架**（Medusa/Saleor）：无自建电商需求，背全套 SKU/购物车/订单模型是纯负债
- **大而全 NestJS starter**：捆着用不上的 RBAC/i18n/payment，不如按官方文档手搓 + 小件（throttler/passport/bullmq）
- **WordPress/Typecho 系**：动态 schema、对比、推荐、ES 同步均超出其模型承载，改到深处不如自研

## 16. 后台管理系统（apps/admin）

> v1.3 决策：**一步到位自研**（Refine + Ant Design 独立 SPA），不采用 AdminJS 过渡方案，不引入 Payload/Directus。后台即唯一主数据录入入口（§4 数据源真理切换）。

### 16.1 定位与边界

- **服务对象**：创始人本人（editor/admin 双角色同体）→ 未来雪友志愿者（editor）→ 未来商用运营（多角色）
- **技术栈**：Refine v4（headless admin 框架，自带资源抽象/权限路由/乐观更新）+ Ant Design 5 + React Query；`apps/admin` 构建为静态产物，Nginx 独立 server block 挂 `admin.` 子域
- **API**：复用 NestJS，新增 `admin` 模块路由组 `/api/admin/*`，全部 `@Roles('editor'|'admin')` + JWT 守卫；与前台共用 packages/schema 的 zod 定义（表单校验与 API 校验同一份）

### 16.2 核心能力（为什么值得自研）

1. **spec_schema 驱动动态表单**（后台的技术核心）：读类目 `spec_schema.fields` 自动渲染录入表单——number 带 min/max、enum 下拉、mult_enum 多选、nested 尺寸表用可编辑行表格。**新增品类 = 零后台代码**，与 §5 多品类原则首尾呼应。
2. **图片管线**：COS STS 直传（不过服务器）→ 自动 webp 压缩 → 3:4 卡图生成预览；素材来源字段强制填写（版权留痕，对应 §11 风险表）
3. **审核工作流**：report 队列（open → resolve/reject，操作即写状态）、评论隐藏/恢复、用户封禁/解封——这类带状态机与副作用的界面是现成 CMS 给不了的
4. **配置中心**：推荐映射表、洞察规则、敏感词从"文件配置"升格为"DB 表 + 后台编辑 + 版本化"——调推荐权重不再需要 CI 发版（v1.3 调整 §6 原则：**领域配置类**改为 DB 版本化存储，**代码类**仍走 Git）

### 16.3 模块清单（随里程碑分两批）

**M2 随图鉴流上线（数据录入必须先行，40 款板子靠它生产）**
| 模块 | 功能 |
|---|---|
| 产品管理 | 列表（筛选/搜索/批量状态）、动态表单编辑、草稿/发布、图片管理 |
| 类目与品牌 | category 树维护、spec_schema JSON 编辑器（zod 校验 + 错误定位）、brand CRUD |
| 榜单管理 | ranking CRUD、rank_entry 拖拽排序、社区投票结果查看 |
| 导入工作台 | Crawlee 采集草稿（YAML）→ 预览 diff → 确认导入（解决"自动采集"与"PG 为主源"的合流点） |
| 登录与权限 | editor/admin 角色登录、会话管理 |

**M3 随社区流上线**
| 模块 | 功能 |
|---|---|
| 审核队列 | report 处理、评论/回复隐藏、用户封禁 |
| 配置中心 | 推荐映射表/洞察规则/敏感词编辑（版本化，一键回滚） |
| 审计日志 | audit_log 查询（谁在何时改了什么，before/after diff 视图） |
| 运营小工具 | 零结果搜索词列表（§12 报表）、推荐结果抽样复核标记 |

**明确后置**：数据看板大页（Umami 已覆盖）、会员管理营销功能（无此业务）、富文本编排（榜单导语用 Markdown  textarea 即可）。

### 16.4 安全（后台比前台重要一个量级）

- `admin.` 子域 **Nginx IP 白名单**（v1 只放行你的固定 IP/家宽+办公网络段），白名单外请求直接 403 且不暴露路径存在
- 账号层：登录挂 T-Captcha + 失败锁定（5 次/15min）；admin 角色操作封禁/删除类需二次输入密码
- 应用层：`/api/admin/*` 全局限流独立于前台桶；写接口一律 zod 白名单 + 禁 mass-assignment
- **审计**：所有后台写操作由 Prisma middleware 自动落 `audit_log`（actor、action、entity、before/after JSONB）——单人项目的误删保险，配合每日备份（§13.4）就是后悔药
- 后台不发 SSR cookie，纯 Bearer token，攻击面与前台隔离；关闭 Refine 默认的 devtools 生产入口

### 16.5 工作量与降级预案

- M2 后台基础版预估 **+3~4 天**（Refine 脚手架 0.5 天，大头在动态表单渲染器 1.5 天 + 图片管线 1 天）
- 若 M2 进度告急的降级顺序：先砍"导入工作台 diff 预览"（直接覆盖导入）→ 再砍榜单拖拽（手输序号）；**动态表单不可砍**，它是后台存在的理由
- 长期红线：后台永远不提供"直接执行 SQL/任意字段覆写"能力，schema 校验是数据质量的最后闸门
