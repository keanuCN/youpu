# 本地全栈验收与阻塞修复设计

## 背景

当前分支 `codex/admin-information-architecture` 已经包含认证、分类目录、搜索筛选、后台管理、评论审核和问卷流程，但项目文档与代码状态尚未完全同步。后续社区能力和线上部署都依赖一条稳定的本地全栈链路，因此先把当前分支验证为可发布候选版本。

## 目标

建立一套可重复执行的本地验收流程，确认 PostgreSQL、Redis、API、前台和后台之间的关键链路正常；同时修复会阻塞开发或部署的基础问题，尤其是可选 Elasticsearch 不可用时健康检查不应卡住。

## 非目标

- 本阶段不新增评分、评论、收藏、通知或推荐业务规则；这些能力只做已有实现的联调验证。
- 本阶段不要求 Elasticsearch 和 Umami 成为本地启动必需服务，PostgreSQL 搜索兜底继续保留。
- 本阶段不重置数据库、不删除本地数据，也不改变生产服务器状态。
- 本阶段不处理分享卡、AI 推荐、支付或其他 M4 能力。

## 现状与问题边界

### 服务依赖

- PostgreSQL 和 Redis 是 API 的必需依赖。
- Elasticsearch 是搜索增强的可选依赖；API 已有 PostgreSQL 搜索路径。
- 前台默认使用本地内容包，配置 `NEXT_PUBLIC_CONTENT_SOURCE=api` 后优先读取 API，失败时回退本地内容包。
- 后台使用 API 的 Bearer 管理令牌，并通过独立的 `apps/admin` 运行在 3002 端口。

### 当前风险

1. `GET /api/health` 会并行检查数据库、Redis 和 Elasticsearch；当环境配置了 `ES_NODE` 但 Elasticsearch 未运行时，健康检查可能等待网络超时。
2. README 中 M2/M3 和线上部署状态描述落后于当前分支提交，容易导致启动和验收步骤被误解。
3. 认证、搜索、后台审核和问卷已经有实现，但缺少一份针对当前分支的真实链路验收清单。

## 方案

### 1. 可重复的验收顺序

验收按以下顺序执行，前一步失败时不把失败归因到后一步：

1. 确认工作树、分支和环境变量来源，不覆盖用户已有的 `.env`。
2. 启动 PostgreSQL 和 Redis；只有需要验证分词搜索时才启动完整基础设施。
3. 执行 Prisma 迁移，并运行数据校验和幂等 seed。
4. 启动 API、前台和后台，检查进程端口与页面响应。
5. 依次验证 API 健康、产品目录、搜索筛选、认证、社区、推荐和后台接口。
6. 验证前台的 API 内容模式、本地回退、图片代理、登录、测验和个人中心入口。
7. 将发现的问题按“阻塞 / 可发布前修复 / 后续优化”分类，先处理阻塞项。

### 2. 健康检查语义

数据库和 Redis 任一不可用时，健康状态为 `degraded`，并明确返回对应布尔值。

Elasticsearch 无配置或不可达时，`es` 返回 `false`，但不会阻塞响应，也不会让仅依赖 PostgreSQL 的 API 失效。检查必须使用有限超时；超时后释放请求并返回降级状态。Elasticsearch 可用时保持现有 `true` 语义。

不改变搜索服务本身的选择逻辑：配置并可用时走 Elasticsearch，未配置或查询失败时继续走 PostgreSQL 搜索和前台本地内容包回退。

### 3. 验收覆盖范围

| 领域 | 验收内容 | 通过条件 |
|---|---|---|
| 基础设施 | PostgreSQL、Redis 容器 | 容器运行且 API 可连接 |
| 数据 | migrate、validate、seed | 命令退出码为 0，产品和分类可查询 |
| API | health、products、search | 返回合法 JSON，关键字段符合共享 schema |
| 认证 | 验证码、注册、登录、刷新、退出、个人资料 | 开发环境可使用返回的 devCode，令牌可完成受保护请求 |
| 社区 | 评论列表/发布、收藏、通知、推荐 | 已登录用户可完成一次最小闭环 |
| 后台 | 令牌、总览、产品编辑、发布、审核、审计 | 修改后的状态可重新读取并留下必要记录 |
| 前台 | 首页、目录、搜索、详情、图片、问卷、个人中心 | 页面可加载，无关键接口未处理错误 |
| 回退 | API 内容模式断开 | 前台显示本地内容包，不白屏 |

### 4. 文档同步

README 只更新与本阶段直接相关的内容：

- 当前分支已经实现的认证、搜索、后台审核和问卷能力。
- 默认本地启动只需要 PostgreSQL 和 Redis。
- Elasticsearch 是可选增强，不是基础开发阻塞项。
- 本地验收顺序和生产部署仍然分开描述。

不在本阶段重写技术设计方案和数据库全量设计文档，避免文档范围扩大。

## 文件边界

实现时优先限定在以下文件或新增小型验收脚本：

- 修改 `apps/api/src/health/health.controller.ts`：实现可选 Elasticsearch 的有限超时健康检查。
- 必要时在 `apps/api/src/health/` 增加与健康检查逻辑对应的单元测试。
- 修改 `README.md`：同步启动、验收和当前状态说明。
- 如现有脚本无法覆盖 Windows PowerShell 的关键路径，再新增一个只读验收脚本；脚本不得删除数据库或覆盖环境文件。

不在本阶段无关地重构 `apps/web`、`apps/admin` 或 Prisma schema。

## 错误处理与安全约束

- 所有验收命令必须使用当前工作树的环境变量，不在仓库写入真实令牌、密码或 SMTP 凭据。
- 健康检查不得把 Elasticsearch 连接错误抛给调用方造成 500；应该返回可解释的降级状态。
- 数据库迁移和 seed 必须使用现有幂等机制，不使用破坏性 reset。
- 认证验收只使用本地测试邮箱和开发环境验证码，不发送真实邮件。
- 发现现有数据不一致时先记录证据，再决定是否修复，不直接覆盖用户数据。

## 测试策略

先为健康检查的 Elasticsearch 超时/不可用行为写失败测试，再实现最小修复并验证通过。已有前台和 API 搜索测试继续作为回归基线；完整类型检查和生产构建在本阶段末尾执行，若资源或正在运行的开发服务冲突，则先停止冲突进程后再执行。

最终验收同时包含：

- 针对性自动化测试。
- 数据迁移、校验和 seed 命令输出。
- API HTTP 响应检查。
- 前台和后台页面 HTTP 检查。
- `git diff`、类型检查和生产构建结果。

## 完成定义

只有满足以下条件才进入第 3 阶段：

1. 阻塞项为 0，或每个剩余阻塞项都有明确原因和用户确认的处理方式。
2. 健康检查在 ES 不可用时能快速降级返回。
3. 数据库、种子数据、API、前台、后台和关键认证链路均有验收证据。
4. README 与当前实现状态一致。
5. 工作树变更经过测试和构建验证，并记录实际结果。
