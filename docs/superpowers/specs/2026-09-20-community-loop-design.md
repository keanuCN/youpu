# 社区评论、评分、收藏闭环设计

状态：已获用户确认，待进入实施计划

日期：2026-09-20

## 1. 背景与目标

有谱当前已经具备账号登录、产品评论、评分、回复、收藏、举报、站内通知和后台基础审核能力，但三条链路仍然是分散的：评论质量控制不完整，举报处理不会完整影响内容状态，收藏与通知缺少可靠的幂等和前台跳转体验。

本阶段将这些能力收敛为一条可验收的社区闭环：用户可以即时发布并维护实测内容，收藏产品后能收到相关社区动态，管理员可以处理举报和风险内容，所有关键状态变化都可追溯。

## 2. 已确认的产品规则

### 2.1 发布策略

- 评论和回复默认发布后立即展示。
- 举报或规则命中不会自动隐藏内容；内容继续展示，同时进入后台待关注或待处理队列。
- 管理员可以忽略举报、处理举报但保留内容、隐藏内容或拒绝内容。
- 只有 `published` 状态的评论和回复参与前台展示、评分统计和“最有帮助”排序。
- 每个账号对同一产品只保留一条评分，重复提交沿用当前更新逻辑。

### 2.2 质量与安全规则

- 发布时检查账号状态、内容长度、重复内容和提交频率。
- 对敏感词、异常评分和异常行为做可解释的风险标记，不在本阶段引入复杂 AI 审核。
- 评论、回复、举报和“有帮助”操作使用 Redis 做频率限制。
- 同一账号对同一评论的“有帮助”投票保持唯一，可切换取消。
- 同一账号对同一目标只能提交一次举报。

### 2.3 通知规则

- 新评论通知所有收藏该产品的用户，但不通知评论作者本人。
- 回复通知原评论作者，但不向自己发送通知。
- “有帮助”通知评论作者，但不向自己发送通知。
- 通知包含目标类型、目标 ID、产品 slug 和前台跳转位置。
- outbox 重试不能生成重复通知。

## 3. 方案与选择

本阶段采用“增量完善现有社区能力”的方案：保留现有 API 路径、账号体系、社区表、outbox worker 和后台审核页面，在其上补充风险标记、幂等通知、筛选、限频、跳转和审计。

不采用完整重做事件驱动社区，因为当前项目已经有可用的 outbox 基础设施；也不只做前台体验，因为评论安全、举报处理和通知幂等必须在 API 与数据库层保证。

## 4. 系统设计

### 4.1 数据模型

- `Rating` 增加 `moderationRisk`、`moderationReasons` 和 `moderationCheckedAt`，用于区分“正常内容”和“待关注内容”；现有 `status` 继续表达公开状态 `published / hidden / rejected`。
- `RatingReply` 使用与 `Rating` 对齐的三个风险标记字段，现有 `status` 继续控制公开状态。
- `Report` 继续使用现有举报表，处理时写入 `handledBy` 和 `handledAt`，并通过审计日志保留变更记录。
- `Notification` 增加 `sourceEventId` 并建立唯一约束，确保同一事件在 worker 重试时只落库一次。
- 为产品评论状态、评论创建时间、回复状态、举报状态和账号通知未读查询增加必要索引。

### 4.2 API 与服务层

保留现有路径：

- `GET /api/products/:productRef/ratings`
- `POST /api/products/:productRef/ratings`
- `DELETE /api/ratings/:id`
- `POST /api/ratings/:id/helpful`
- `POST /api/ratings/:id/replies`
- `DELETE /api/replies/:id`
- `POST /api/reports`
- `POST/DELETE /api/products/:productRef/favorite`
- `GET /api/me`
- `GET /api/me/favorites`
- `GET/PATCH /api/me/notifications`

评论查询增加可选参数：

- `sort=helpful | latest | similar`
- `profile=complete`：只看带完整使用条件的评论
- `level=beginner | intermediate | advanced | expert`：按使用水平筛选
- `sort=similar` 仅对已登录用户按其账号资料计算；游客请求自动回退到 `helpful`

旧请求不带这些参数时保持当前结果。

### 4.3 评论质量与评分统计

- 评分统计只读取已发布评论。
- 支持“最有帮助”“最新发布”“与我相似”三种排序。
- “与我相似”根据评论保存的使用条件计算，优先匹配使用水平，其次匹配身高 / 体重等可用条件，并优先展示完整资料。
- 评论被隐藏或拒绝后发出 `rating.changed` outbox 事件，重新计算产品评分和评分分布。
- 当前每产品每账号唯一评分约束保留不变。

### 4.4 收藏与通知数据流

收藏接口保持幂等。产品卡片、详情页和个人中心统一以云端账号数据为准，游客态继续使用本地状态。

评论、回复和有帮助操作在业务事务中写入 outbox 事件；通知消费者带着来源事件 ID写入通知表。通知点击后根据目标信息跳转到产品详情页的评论区、指定评论或个人中心评论列表，并先将通知标记为已读。

通知生成必须排除操作人本人，并通过来源事件唯一约束抵御 outbox 重试。收藏取消不会删除历史通知。

### 4.5 后台审核

后台“内容审核”页面继续只使用中文界面，分为举报队列和评论队列：

- 举报队列展示目标、原因、补充说明、举报人、状态、处理人和时间。
- 评论队列展示产品、作者、评分、使用条件、内容、有帮助数、风险标记和状态。
- 管理员可以忽略、处理、隐藏、拒绝和重新打开对应记录。
- 编辑角色可以查看社区数据，但只有管理员可以执行审核状态变更。
- 所有审核变化写入操作审计，包含操作人、对象、变更前状态和变更后状态。

## 5. 错误处理

- 未登录的评论、回复、收藏、举报和有帮助操作返回统一登录提示。
- 重复举报返回明确的冲突提示，不创建第二条记录。
- 频率超限返回可理解的稍后再试提示，前台不清空用户已填写内容。
- 内容被隐藏或拒绝后，前台不再将其计入列表和统计；个人中心仍保留作者查看自己的记录所需的状态信息。
- 云端请求失败时，前台保留本地内容包和游客态，收藏操作失败时恢复本地按钮状态。
- 通知加载失败只影响通知区域，不阻塞产品详情或个人中心其他区域。

## 6. 实施阶段

1. 数据库与 API：风险标记、通知去重、查询参数、限频和审核状态联动。
2. 前台社区：评论排序筛选、收藏状态同步、通知跳转和异常提示。
3. 后台审核：风险内容展示、举报处理、内容状态变更和中文文案。
4. 测试与文档：补齐 API、权限、通知、前台回退和后台操作测试，并更新 README。

## 7. 验收标准

- 评论和回复默认即时可见。
- 举报和规则命中内容可以在后台被处理。
- 隐藏 / 拒绝内容不参与前台展示和评分统计。
- 同一账号对同一产品只能保留一条评分。
- 收藏状态在卡片、详情页和个人中心一致。
- 新评论、回复和有帮助通知只生成一次，并可跳转到对应内容。
- 评论、回复、举报和有帮助操作均具备频率限制。
- 审核操作记录管理员和审计日志。
- 后台管理页面不出现不必要的英文内容。
- 现有登录、搜索、产品资料、人民币价格和数据分析能力不受影响。

## 8. 非目标

- 本阶段不引入 AI 自动审核。
- 本阶段不新增公开私信、关注用户、粉丝关系或社交首页。
- 本阶段不重做现有账号系统和 outbox 架构。
- 本阶段不修改产品资料、搜索筛选和人民币价格的业务规则。
